- パスワードリセット・メールアドレス確認（要件定義書に記載がないため対象外。ログイン情報を忘れた場合の救済フローは今回設けない）
- 記録の公開・他ユーザーからの閲覧（下記3.4節参照。全記録は本人のみ閲覧可能） 
- 発行済みアクセストークン自体の即時失効（ブラックリスト等）。リフレッシュトークンはサーバー側で失効させられるが、既に発行済みのアクセストークンはステートレスなJWTのため、自然に有効期限が切れるまで（最大1時間）は理論上使用可能（[auth-design.md](./auth-design.md) 4-2節）
- [requirements.md](./requirements.md) 3.2に記載の拡張機能（逆方向提案、紅茶等への対応拡大、S3本格保存、Instagram連携）

## 3. 機能詳細

### 3.1 ユーザー認証（S1, S2）

**新規登録**
- 入力項目：メールアドレス・パスワード
- メールアドレスは形式チェック＋重複チェック（登録済みの場合は409 `EMAIL_ALREADY_EXISTS`）
- パスワードは8文字以上、72文字以下（BCryptの仕様上の上限。[api-spec.md](./api-spec.md) 3.1）
- パスワードはBCryptでハッシュ化して保存し、平文は保持しない
- 登録成功時はアクセストークン・リフレッシュトークンの両方を発行し、自動ログイン状態でS3（ペアリング提案画面）に遷移する。ログイン画面への再遷移は挟まない（[screen-flow.md](./screen-flow.md) 3章）

**ログイン**
- メールアドレス＋パスワードで認証
- 失敗時は401 `INVALID_CREDENTIALS`。メール・パスワードのどちらが誤りかは特定させない文言にする（総当たり攻撃でのアカウント存在確認を防ぐため）
- 成功時はアクセストークン・リフレッシュトークンの両方を発行する

**トークンの有効期限とリフレッシュ**
- アクセストークン：1時間。リフレッシュトークン：14日間（[auth-design.md](./auth-design.md) 3章）
- アクセストークンが期限切れになった場合、フロントエンドは保持しているリフレッシュトークンで自動的に再発行を行い（`POST /api/auth/refresh`）、ユーザーからは意識されない形で処理を継続する。リフレッシュトークン自体も無効・期限切れの場合のみ、S1（ログイン画面）へ強制的に遷移させる
- リフレッシュトークンは使用のたびにローテーション（古いものを失効させ新しいものを発行）する。漏洩したトークンが再利用された場合は401として検知する（[auth-design.md](./auth-design.md) 4-2節）

**ログアウト**
- S3・S4のヘッダーに置いたログアウト操作から、保持しているリフレッシュトークンを添えて`POST /api/auth/logout`を呼び出し、サーバー側で当該リフレッシュトークンを失効させる。あわせてクライアント側でもアクセストークン・リフレッシュトークンを破棄し、S1へ遷移する（[screen-flow.md](./screen-flow.md) 4章）

**認証ガード**
- 未ログイン状態、または有効期限切れ・改ざんされたアクセストークンで保護対象APIにアクセス → 401 `UNAUTHORIZED`

**認可（本人確認）**
- 記録（`records`）の閲覧・編集・削除は、その記録を作成した本人のみ可能。他人の記録IDを指定した場合は404 `NOT_FOUND`（存在しない場合と区別しない。連番IDのため403で「存在するが自分のものではない」と教えてしまうと総当たり攻撃の標的になる。下記ペアリング提案IDの方針と統一。[api-spec.md](./api-spec.md) 3.7〜3.9）
- ペアリング提案（`pairing_suggestions`）を記録に紐付ける際も、自分自身が作成した提案IDのみ指定可能（他人の提案IDを指定した場合は404 `NOT_FOUND`。存在確認と所有権確認を区別しないことで、他人の提案IDの存在有無を推測されないようにする）

### 3.2 ペアリング提案（S3, S5）

提案は2段階のAI呼び出しで構成する：①追加質問の生成、②追加質問への回答を踏まえた最終提案。

1. スイーツ名（1〜100文字、必須）を入力し、「AIに提案してもらう」ボタンでリクエストする（`POST /api/pairings/questions`）
2. AIがスイーツ名から、コーヒー豆選定に役立つ追加質問を1〜2問、それぞれ3〜4個の選択肢とともに動的に生成する（味の系統・主な材料など、質問内容自体もAIが判断する）。ユーザーはすべての質問に選択式で回答する（自由記述は不採用）
3. 全問回答後、スイーツ名と回答内容をあわせて最終提案をリクエストする（`POST /api/pairings`）。AIには `coffee_beans` マスタ10種（[database-design.md](./database-design.md) 2.2節）の中から1件を選ばせ、選定理由を生成させる。選択肢の範囲外の豆をAIが返した場合はサーバー側でエラー扱いとする（502 `AI_SERVICE_ERROR`）

- S3（ペアリング提案画面）だけでなく、S5（記録作成画面）の入り口②（S4の「＋」から開いた場合）でも、フォーム内のAI提案エリアから同じ操作で提案を取得できる（[screen-flow.md](./screen-flow.md) 1章）。処理内容・利用上限は画面によらず共通
- ボタン押下前に、本日の残り利用回数を画面に表示する（`GET /api/pairings/usage`）
- **利用上限**：1ユーザー1日5回まで。JST（日本時間）の0時を境に1日をリセットする（[database-design.md](./database-design.md) 3章 決定事項No.3）。質問生成（上記1〜2）は利用上限のカウント対象外とする（何度呼び出しても消費しない）。追加質問ステップの導入でAI API呼び出し回数自体は増えるため、コスト増を抑える目的で上限を10回から5回に引き下げた
  - 上限に達している場合、質問生成（`POST /api/pairings/questions`）の時点でサーバー側が弾く（429 `RATE_LIMIT_EXCEEDED`）。UIは「AIに提案してもらう」ボタンを非活性にし、リセット時刻をあわせて表示する。質問ステップの後で上限に達することはない（質問ステップ開始前にチェック済みのため）
- **カウント方法**：最終提案（`POST /api/pairings`）のAI API呼び出しが成功し `pairing_suggestions` に1件保存された時点でカウントする。AI API呼び出しがエラー（タイムアウト・障害等）になった場合はカウントに含めない（ユーザーの落ち度ではない失敗でクォータを消費させないため）。質問生成の呼び出しはそもそも何も保存しないため、この時点ではカウントされない
- 提案結果は画面に表示され、そのまま「記録として保存」ボタンでS5（記録作成画面）に遷移できる。保存しなくても提案結果の閲覧のみで完結してよい（保存は任意）

### 3.3 記録の保存（S5）

- 入力項目：スイーツ名（必須・1〜100文字）、記録日（必須）、写真（任意）、感想（任意・最大1000文字）
- 記録の作成には2つの入り口があるが、S5の画面自体は共通で、AI提案エリアはどちらの入り口でも表示される（[screen-flow.md](./screen-flow.md) 1章）
  1. S3のペアリング提案結果から保存：`pairingSuggestionId` を伴った提案結果がプリセットされた状態で開く
  2. S4の「＋」ボタンから直接作成：提案が未取得の状態で開く。フォーム内の「AIに提案してもらう」ボタンから提案を取得すれば入り口①と同じ状態になり、取得しなければ `pairingSuggestionId` はなし・コーヒー豆名・理由もnullのまま保存される
- 保存時点でフォームに表示されているAI提案（取得していれば）の`pairingSuggestionId`を記録に紐付け、提案時点のコーヒー豆名・理由をスナップショットとして記録にコピーする（[database-design.md](./database-design.md) 2.4節）
- 1つのAI提案から作成できる記録は最大1件（`pairing_suggestion_id`のUNIQUE制約。[database-design.md](./database-design.md) 2.4節）。既に記録に使われた提案IDを再指定した場合は409 `PAIRING_SUGGESTION_ALREADY_USED`とする
- 1人のユーザーが同じ日付に複数件の記録を保存することを許容する（[database-design.md](./database-design.md) 3章 決定事項No.1）
- 写真は任意項目とする（写真なしで記録を保存できる）。アップロードされた場合はjpg/png・最大5MBまでとし、EC2ローカルディスク（EBS）に保存する（[aws-infra-design.md](./aws-infra-design.md)参照）

### 3.4 記録一覧表示（S4）

- ログイン中のユーザー自身が保存した記録のみをカレンダー形式で表示する。他ユーザーの記録は一切表示しない・取得できない（「インスタグラム風のUI」は写真中心のグリッド表示という見た目上の参考であり、他ユーザーへの公開・閲覧を意味するものではない。[requirements.md](./requirements.md) 1.1の想定用途は個人の記録・振り返りである）
- 表示は月単位で取得する（`GET /api/records?year=&month=`）。月を送ることでカレンダーを前後に移動できる
- タブを開いた時点の初期表示月は常に「実際の今日時点の月」とする。カレンダー内で前後の月に移動した状態で他のタブに切り替えて記録タブに戻ってきた場合も、閲覧中だった月は保持せず今日の月に戻す（保存済み記録がある月を優先して表示する、といった動作はしない）
- 同一日に複数記録がある場合、日付セルには代表1枚のサムネイルと件数バッジ（例：`🖼×2`）を表示する（[wireframes.md](./wireframes.md) S4参照）
- 記録が0件の月も、空のカレンダーとして正常に表示する（エラー扱いにしない）
- 記録がない日付セルをタップした場合、S5（記録作成画面）へ遷移する。ヘッダーの「＋」ボタンからの遷移と同じ空の状態だが、日付欄の初期値はタップした日付になる（[screen-flow.md](./screen-flow.md) 1章）

### 3.5 記録の編集・削除（S6, S7）

**編集**
- 編集可能な項目：スイーツ名、記録日、写真、感想
- 編集不可な項目：AI提案結果（`pairingSuggestionId` / コーヒー豆名 / 理由）。AI提案はその時点のスナップショットであるため、後から編集や再提案を行う機能は設けない（提案をやり直したい場合は記録を削除して作り直す運用とする）
- 写真を変更しない場合は既存の写真をそのまま保持する。既存の写真を削除して「写真なし」の状態にしたい場合は、`deletePhoto`フラグを`true`で送信する（[api-spec.md](./api-spec.md) 3.8）。この場合、DB上の`photo_path`をNULLに更新し、サーバー上の画像ファイルも削除する

**削除**
- 本人の記録のみ削除可能（3.1節の認可ルール）
- 削除確認ダイアログを挟んでから実行する（[screen-flow.md](./screen-flow.md) 3章）
- 削除は物理削除。DBレコードの削除とあわせて、保存されている写真ファイルもサーバーから削除する（[database-design.md](./database-design.md) 3章 決定事項No.5）。ファイル削除に失敗した場合でもDBレコードの削除は完了させ、孤立ファイルの掃除は別途バッチ等で対応する方針とする（同期的にファイル削除を保証すると、ストレージ障害時にユーザーの削除操作自体が失敗してしまうため）
- **実装上の注意（処理順序）**：「DB削除→ファイル削除」の順序で実装する場合、DB削除のトランザクションがロールバックされた後にファイルだけ消えてしまうと、DBには記録が残るのに画像ファイルが存在しない不整合が起きる。これを防ぐため、画像ファイルの物理削除はDBトランザクションが**コミットされた後**に実行する（例：Springの`@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)`を利用する）
